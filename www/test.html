A · Does Emergency Stop correctly invalidate position?

audit finding F-1 · canonical machine-frame invalidation
Emergency Stop uses M410, which can stop the machine between planned motion segments. After that the software must no longer trust its exact position until Home All is completed again.

Why are we testing this?

Emergency Stop uses M410, which can stop the machine between planned motion segments. After that the software must no longer trust its exact position until Home All is completed again.

checking...

Before you start

Required: safety pre-flight, machine ONLINE, frame TRUSTED, work zero VALID. The readiness panel above shows the live check.

What do I do?

  1. Home All. (blocking, up to ~1 minute)
  2. Set the Work Zero (normal CNC UI, Zero section).
  3. Confirm the frame shows TRUSTED.
  4. Open the normal CNC controls.
  5. Begin a slow X/Y jog.

B · Can two motion systems ever take control at the same time?

audit finding F-3 · canonical motion-stream admission
The jog system, job streams (normal job, test motion, production resume) and machine operations (Home/Zero) must never drive the machine at the same time. Exactly one motion owner is allowed.

B1 Active job blocks jog

Why are we testing this?

While a job is streaming motion, the jog system must be locked out. Two motion sources on one machine would fight over the actual tool movement.

checking...

What do I do?

  1. Start an air-only job or test motion in the normal UI.
  2. While it is running, attempt a jog from the normal UI joystick.
  3. Watch the refusal and confirm the running stream is undisturbed.
WHAT SHOULD I SEE? HTTP 409 "jog rejected while a job is active" (direct call) or the same refusal shown in the UI. The running stream keeps running and completes normally. The job must NOT pause, stop, or error because of the jog attempt. Expected HTTP: 409 (meaning: the jog was refused before anything was sent to the machine).
Did everything above happen exactly as described?
What went wrong?
STOP this subsystem's test sequence. Do not continue with later steps for this finding.

D · Can a job start without firmware permission?

audit finding F-5 · firmware-issued one-time start capability
The job file on the SD card is written by the browser. Nothing in it may authorize a start. Only a short-lived capability minted by firmware - after firmware checked the real files and the machine frame - may start a job, and it works exactly once.

Prepare the job identity

Why are we testing this?

The tests below need the identity of a real prepared air-only job. This page reads the prepared sidecar through the existing file API - it never computes fingerprints itself and never creates authorization.

No hidden setup: prepare an air-only test job

  1. Open the normal CNC UI. Keep the router physically disconnected.
  2. Select a small existing G-code file (a few lines are enough).
  3. Complete the normal Preview/verification flow (Home All, Work Zero, Bounds/Aircut check) until Start Cutting is available.
  4. Return here when Start Cutting is available.
checking...
WHAT SHOULD I SEE? "Prepared job detected" once a sidecar with valid active-run evidence has been loaded. The page shows the identity claims it read (mode, size, work-zero id). Firmware re-validates all of it - including re-hashing the actual run file - at authorize and again at start.

D4 Identity mutation

checking...

C · Can recovery motion bypass firmware safety?

audit finding F-2 · firmware-owned recovery authority
Recovery moves reposition the machine after an interrupted job. Firmware alone decides when they are allowed - from its own frame trust, never from anything the browser reports.

C1 Enter RECOVERY_REQUIRED

Why are we testing this?

In this test we intentionally turn a safe Pause into RECOVERY_REQUIRED by asking to jog while paused. The machine should not jog immediately. Instead, firmware first invalidates direct Resume and the position frame, and requires a recovery review.

checking...

What do I do?

  1. Start a tiny air-only job (Test D2 or the normal UI).
  2. Pause it (intact pause).
  3. While PausedIntact, attempt a jog in the normal UI.
  4. Expect the refusal below - that refusal is the correct behavior, not a bug.
WHAT SHOULD I SEE? HTTP 409 "direct Resume was invalidated; wait for RECOVERY_REQUIRED before jogging". Job: RECOVERY_REQUIRED. Frame: UNTRUSTED (the interruption invalidates position trust). The checkpoint evidence is persisted before the frame is dropped. The machine must NOT jog while paused intact. Expected HTTP: 409 (meaning: firmware protected the resumable pause).
Did everything above happen exactly as described?
What went wrong?
STOP this subsystem's test sequence. Do not continue with later steps for this finding.
